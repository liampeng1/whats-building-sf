# Verified Zoning-Rules Data — Design Spec

**Date:** 2026-05-31
**Status:** Draft for review
**Author:** Liam Peng (with Claude)

## Problem

The zoning side-panel shows detailed rules (density, FAR, parking, setbacks, uses)
from a hand-maintained table in `lib/zoning-rules.ts`, looked up by `getZoningRecord(code)`.
Two defects:

1. **Coverage gaps.** 19 DataSF districts have no record (e.g. `RM-2`, `RM-3`,
   `RM-4`, `RTO-1`, `UMU`), so their panels fall back to a generic "not transcribed
   yet" message — the reported "no info" for `?district=RM-2`.

2. **The existing 52 records are unverified and contain errors.** Git history shows
   they were generated by AI agents (Claude Sonnet 4.6 → Opus 4.7) from training
   data, not transcribed from the code, then stamped with `§`-citations. Comparing
   against the official source proved concrete errors, e.g. for `RH-1`:
   - `rear_ft: 25` — a misread of "25% of lot depth" (a percentage, not feet).
   - `lot_coverage_max_pct: 45` — fabricated; 45% is a *different* district's
     *rear-yard* rule, and RH-1 has no lot-coverage rule at all.
   - `density: { units_per_lot: 1 }` — drops the "up to 1 per 3000 sf, max 3 units,
     with CU approval" pathway.

   The citations create an impression of authority the values do not honor.

Additionally, the citation **URLs are broken**: `cite()` builds
`…/sf_planning/0-0-0-209`, but amlegal's real anchors are opaque IDs (§207 is
`0-0-0-19952`). Today's links redirect to the code front page.

## Goals

- Replace the zoning-rules data with values transcribed from **authoritative,
  pointable sources**, each field carrying a **verbatim source quote**.
- Make "verified" mechanically checkable (tests fail if a value isn't backed by
  its quote, or if a source link is wrong).
- Give the end user real, clickable provenance: the source document, the exact
  code section, and the verbatim code language.
- Keep the data as version-controlled source (not a DB) — the git diff +
  per-field citation is a superior audit trail for legal reference data.

## Non-goals

- No database. Storage stays a typed data file; this is read-only reference data
  (~71 rows) changing a few times a year.
- Phase 1 does **not** cover non-residential districts (see Phasing).

## Sourcing — what the POCs established

| Source | Reachable how | Verdict |
|---|---|---|
| SF Planning **Residential Districts Controls Summary Table** (PDF) | WebFetch-download → `Read` as PDF | **Primary source for Phase 1.** Authoritative, pre-tabulated to our fields, `§` in every column header. Confirmed readable. |
| `codelibrary.amlegal.com` (canonical Planning Code) | Real browser only (WebFetch → 403); opaque section IDs | Source of **correct per-section deep-links**. §207 → `0-0-0-19952` confirmed resolves to "SEC. 207…". |
| `sf-ca.elaws.us` mirror | WebFetch (503 once; retryable) | Unofficial, HTTP-only, flaky. Fallback only. |
| DataSF Zoning Districts `3i4a-hu95` | Already fetched at build | District list + geometry + `codesectio` (drives the build-coverage guard). |

PDF URL: `https://default.sfplanning.org/publications_reports/residential_districts_controls_summary_table.pdf`
(rev. 09/2008 — the current published edition).

## A. Data flow

```
Official SF Planning summary PDF ──download──▶ Read-as-PDF ──▶ verbatim table text
                                                                      │
                              committed once as __fixtures__/zoning/residential-summary.txt
                                                                      │
                                            transcribe each field WITH its verbatim quote
                                                                      ▼
                            lib/zoning-rules.ts ──▶ invariant tests + build coverage guard
                                                                      ▼
                                                       ZoningDistrictPanel renders rules
                                                       + verbatim quotes + real source links
```

## B. Schema

Keep the existing "flat values + `source` block" shape (minimises consumer churn).
Changes: every citation gains a verbatim `quote`; add new fields; fix the mismodelled ones.

```ts
interface CodeCitation {
  section: string   // "§207"
  url: string       // built from SECTION_URL opaque-ID map (real amlegal anchor)
  quote: string     // verbatim source sentence supporting the value
}

interface DensityRule {
  units_per_lot?: number   // base "3 units per lot"
  sqft_per_unit?: number   // "1 per 600 sf"
  max_units?: number       // CU cap, when applicable
  cu_pathway?: string      // verbatim conditional-use escalation text
  note?: string
}

interface ZoningRecord {
  code: string
  name: string                       // "Mixed (Apartments and Houses), Moderate Density"
  classification: CodeCitation       // §206.2

  density: DensityRule
  far_non_residential?: { max: number }   // PDF's "(Other than Dwellings)"
  min_lot?: { width_ft: number; area_sqft: number }
  open_space_per_unit?: { private_sqft: number; note?: string }
  principal_uses: string[]
  conditional_uses?: string[]
  front_setback_text?: string        // verbatim formula — NOT a parsed number
  rear_yard_text?: string            // verbatim formula
  dwelling_unit_mix_text?: string    // §207.6 (RTO etc.)
  parking_text?: string

  source: {
    density: CodeCitation
    far_non_residential?: CodeCitation
    min_lot?: CodeCitation
    open_space?: CodeCitation
    principal_uses: CodeCitation
    conditional_uses?: CodeCitation
    front_setback?: CodeCitation
    rear_yard?: CodeCitation
    dwelling_unit_mix?: CodeCitation
    parking?: CodeCitation
    retrieved_at: string             // ISO date
    document: string                 // human name of the source doc
    document_url: string             // the PDF
  }
}
```

**Deletions / corrections baked in:**
- `far.max` → `far_non_residential.max` (the PDF says "Other than Dwellings"; it is
  not a cap on housing).
- `lot_coverage_max_pct` — **removed** (never existed; was a misread rear-yard %).
- `setbacks: { front_ft, rear_ft, side_ft }` — **removed**; replaced by
  `front_setback_text` / `rear_yard_text` verbatim, since the real rules are
  formulas ("25% of lot depth, min 15 ft"; "average of adjacent buildings").

### Worked example — `RM-2` (fully verified from the PDF)

```ts

  principal_uses: ['Multi-family dwelling', 'Group housing, boarding', 'Group housing, religious orders'],
  conditional_uses: ['Group housing (medical/educational institutions)', 'Hotel up to 5 rooms'],

    open_space: cite('§135',   '80 sq.ft. per unit if all private; common space substituted must be 1/3 greater'),
    principal_uses:   cite('§§209–209.9', 'Same uses as above, plus: Group housing, boarding; group housing, religious orders'),
    conditional_uses: cite('§§209–209.9', 'Same uses as above, excluding those listed in previous column as principal uses'),
    front_setback: cite('§132', 'Based upon average of adjacent buildings; up to 15 ft. or 15% of lot depth'),
    rear_yard:  cite('§134',   '45% of lot depth, except of reductions based upon average of adjacent buildings…'),

```

### Transcription gotcha — "same uses as above"

The PDF's use columns use vertical "same as above" spanning. Principal/conditional
uses must be **resolved** by reading up the column; the stored `quote` captures the
resolved text so a reviewer can verify without re-deriving the inheritance.

## C. Verification harness

Four mechanical invariant tests in `__tests__/zoning-rules.test.ts`:

1. **Value-appears-in-its-quote.** Every numeric value must be a substring of its
   own `quote` (`sqft_per_unit: 600` ⟹ quote contains `"600"`). Ties each number to
   the source text; catches transcription typos automatically. *This is the test
   that makes "verified" real.*
2. **Monotonic density ramp.** `sqft_per_unit` non-increasing RM-1→RM-4
   (800 ≥ 600 ≥ 400 ≥ 200).
3. **Monotonic FAR & open-space ramps.** `far_non_residential.max` non-decreasing
   (1.8 → 4.8); `open_space_per_unit.private_sqft` non-increasing (100 → 36).
4. **Completeness & link integrity.** Every value field has a non-empty `quote`;
   every cited `§` exists in `SECTION_URL`; the build coverage guard
   (`scripts/build-cross-stats.ts`) still requires every DataSF code to have a
   record or a `KNOWN_NO_RULES` entry.

**Section-link verification.** A one-time capture step navigates the browser to each
`SECTION_URL` entry and asserts the page title matches the section number, so no
broken citation link can ship. The captured ID map is committed.

## D. Sources & transparency (end-user-facing)

Three tiers of real, verified links replace today's broken ones, surfaced in the
panel's "Sources" block:

1. **Per-record document.** Links the official SF Planning summary PDF by name:
   *"SF Planning — Residential Districts Controls Summary Table ↗"*.
2. **Per-rule code deep-link.** Each `§` resolves to its real amlegal anchor via the
   captured opaque-ID map:
   ```ts
   const SECTION_URL: Record<string, string> = {
     '§207':   '0-0-0-19952',  // verified → "SEC. 207. DWELLING UNIT DENSITY LIMITS."
     '§209.2': '0-0-0-56337',
     // §121, §124, §132, §134, §135, §206.x, §151.1, §261 … captured + verified once
   }
   ```
3. **Verbatim code language shown to users.** Because each value stores its source
   sentence, the panel reveals *"what the code says"* inline (e.g. under a rule row
   or on tap) — e.g. `"one dwelling unit per 600 sq.ft. of lot area"`. Provenance
   becomes a feature.

Existing DataSF dataset + SF Property Information Map links remain (boundary/parcel side).

## E. Consumer impact

The record shape is consumed in exactly one place plus tests (verified via grep):

- **`components/ZoningDistrictPanel.tsx`** (lines ~138–191) — render new rows
  (open space, min lot, conditional uses, density pathway), drop lot-coverage,
  show yards as text, surface verbatim quotes + corrected source links. Most-touched
  file.
- **`__tests__/zoning-rules.test.ts`** — replace value assertions; add the four invariants.
- **`scripts/build-cross-stats.ts`** — `KNOWN_NO_RULES` shrinks as residential codes
  gain real records; guard logic unchanged.
- **`lib/family-zoning.ts`** — no impact (its "density" references are the
  density-bonus *law*, not the record shape).

## F. Phasing

- **Phase 1 (this spec).** Residential family — `RH-1`, `RH-1(D)`, `RH-1(S)`, `RH-2`,
  `RH-3`, `RM-1`, `RM-2`, `RM-3`, `RM-4`, `RC-3`, `RC-4`, `RED`, `RTO` (and the
  `RTO-1`/`RTO-M`/`RTO-C` variants mapped as applicable) — all from the one validated
  PDF. Build the schema, the harness, the section-ID map, and the panel updates;
  prove the entire source→transcribe→verify→test→render loop end-to-end.
- **Phase 2 (follow-up spec).** NC/NCT, C, M, PDR, mixed-use, redevelopment districts.
  Requires locating companion summary tables (Commercial/Industrial §§210–227) or
  falling back to the code mirror / amlegal-via-browser. Re-verify and replace the
  remaining AI-generated records, then mark the legacy records gone.
